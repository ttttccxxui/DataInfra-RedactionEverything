## 1. 安装环境确认

> 目标：在现场逐项验证「硬件 → 系统 → GPU 驱动 → 运行时 → 容器 → 网络 → 存储 → 安全」八个环节。

### 1.1 硬件拓扑

| 项目 | 标准基线 | 现场值 | 校验命令 | 负责人 |
|---|---|---|---|---|
| 机型 | 单机 2 × NVIDIA GPU | | `lscpu；dmidecode -s system-product-name` | |
| GPU | ≥2 张，单卡 ≥16 GB | | `nvidia-smi --query-gpu=name,memory.total` | |
| 显存占用 | 部署前 ≤20% | | `nvidia-smi` | |
| CPU | ≥16 核 | | `nproc` | |
| 内存 | ≥64 GB | | `free -h` | |
| 系统盘 | ≥256 GB | | `df -h /` | |
| 数据盘 | ≥1 TB SSD，挂载 `/data` | | `df -h /data；lsblk` | |
| 网卡 | 千兆/万兔自适应 | | `ip -br addr` | |

### 1.2 操作系统与内核

| 项目 | 标准 | 校验 | 负责人 |
|---|---|---|---|
| OS | Ubuntu 22.04 LTS / 24.04 LTS | `cat /etc/os-release` | |
| 内核 | ≥6.5 | `uname -r` | |
| 是否做过最小化安装（无 GUI） | 推荐 | `systemctl list-unit-files --type=service \| grep -E 'ssh\|networkd'` | |

### 1.3 GPU 驱动 / CUDA 栈

| 组件 | 规定版本 | 校验命令 | 负责人 |
|---|---|---|---|
| NVIDIA 驱动 | ≥570（匹配 CUDA 12.8+） | `nvidia-smi`（顶栏 driver 版本） | |
| CUDA | 12.8 | `nvcc --version`；`/usr/local/cuda-12.8/version.json` | |
| cuDNN | 9.x | `cat /usr/local/cuda/include/cudnn_version.h` | |
| 容器运行时 | nvidia-container-toolkit | `/usr/bin/nvidia-ctk runtime configure --runtime=docker；docker run --gpus all nvidia/cuda:12.8.0-base-ubuntu22.04 nvidia-smi` | |

> 驱动与 CUDA 版本不匹配会直接导致 `RuntimeError: no kernel image is available` 或 vLLM 启动失败；遇到时优先在 P0 窗口统一重装。

### 1.4 服务端口与网络

| 服务 | 容器网络名 | 端口 | 说明 | 外网可达 |
|---|---|---|---|---|
| Frontend | frontend | 3000 | 用户工作台 | 仅内网/代理 |
| Backend | backend | 8000 | REST + WebSocket + 任务队列 | 仅内网/代理 |
| HaS Text (vLLM) | ner | 8080 | 语义 NER | 仅网关 → API |
| OCR (PP-StructureV3) | ocr | 8082 | 扫描件/图片 OCR | 仅网关 → API |
| LocateAnything | visual-features | 8090 | 人脸/印章/签字定位 | 仅网关 → API |
| PaddleOCR-VL（可选） | ocr-vl | 8118 | 视觉补充 OCR | 仅网关 → API |

网络放通清单（现场确认）：

- 办公网 → 平台地址:3000 / :8000；
- API 网关 → 8000 → 8080/8082/8090/8118；
- 若启用 LDAP/AD：8000 → LDAP 389/636；
- 若启用数据库直连：8000 → PostgreSQL 5432 / MySQL 3306（仅只读）；
- 若启用 SFTP 拉取：8000 → 远端 22；
- 如使用 `TRUSTED_PROXIES`：代理服务器 IP/CIDR 列表。

### 1.7 运行时配置（生产 env 核对）

> 以下为 **生产环境必须复核** 的关键参数。现场一项一项回填。

| 参数 | 生产值 | 说明 | 核实人 |
|---|---|---|---|
| `AUTH_ENABLED` | `true` | 必须开启认证 | |
| `JWT_SECRET_KEY` | 32 字节强随机（`openssl rand -hex 32`） | 外部文件加载，禁止硬编码 | |

| `JOB_CONCURRENCY` | 按 GPU 数定：双卡 3 / 共享卡按租户分配 | 识别队列并发 | |
| `BATCH_RECOGNITION_PAGE_CONCURRENCY` | 1（共享 GPU） | 并发页数 | |
| `HAS_NER_MAX_PARALLEL_REQUESTS` | 1（共享 GPU） | NER 串行 | |
| `VISUAL_FEATURES_CONCURRENCY` | 1（共享 GPU） | 视觉串行 | |
| `MAX_FILE_SIZE` | 52 MB | 上传限流 | |
| `LOG_JSON` | `true` | 结构化日志 | |

### 1.8 安全基线（部署前 checklist）

- [ ] `AUTH_ENABLED=true`；
- [ ] `JWT_SECRET_KEY` 存于 `~/.redaction_secrets`（`chmod 600`），环境变量通过 `--env-file` 注入；
- [ ] 生产环境关闭 OpenAPI：容器内 `app/main.py` 删除或 gate `DocsRoute` by env；
- [ ] 反向代理套 TLS（Let's Encrypt / 内网 CA）；
- [ ] 上传/输出目录禁 `exec`，挂 `noexec,xfs`?
- [ ] `auth.json`、SQLite、uploads、outputs 纳入备份及访问控制；
- [ ] 首次安装由第一个注册账号初始化 `super_admin`，禁止留默认管理员。

## 2. 实施部署计划

### 2.1 服务注册与端口地图（容器 Compose）

`docker-compose.yml` 编排：`frontend`（3000）、`backend`（8000）、`ner`（vLLM 8080）、`ocr`（8082）、`visual-features`（8090）、`ocr-vl`（8118，`--profile gpu` 可选）。容器间以服务名联通，暴露端口仅经 API 网关。

部署前提：服务器本地已拉 `vllm/vllm-openai:v0.19.1`，OCR/LA 镜像离线导入，HF 模型落位 `~/redaction-deploy/backend/models/*`。

### 2.2 部署步骤（裸机双卡，按 `deploy/dual-5090/start_all.sh`）

1. **拉镜像与模型**：`bootstrap.sh`（执行步骤详见 Runbook）；
2. **落位代码**：`~/redaction-deploy/{backend,frontend/dist}`；
3. **落位脚本**：`deploy/dual-5090/*.sh` → `~/`，GPU 钉卡与显存配额勿改；
4. **配置密钥**：编辑 `backend_g0.sh` → `JWT_SECRET_KEY`（必改）、`AUTH_ENABLED=true`；
5. **启动**：`bash ~/start_all.sh`（自愈式：只拉起 DOWN 的服务；VL 服务就绪 1~3 min）；
6. **验收**：`curl localhost:8000/health/services → all_online:true`；执行 `e2e/` Tier-1 冒烟。

### 2.3 健康检查与自愈

| 探针 | 接口 | 周期 | 动作 |
|---|---|---|---|
| 服务就绪 | `GET /health/services` | 30s | 挂掉服务 `start_all.sh` 重拉 |
| GPU 健康 | `gpu-util`（钉卡脚本） | 5s | 显存>95% 告警 |
| 队列僵死 | 任务 30s 无推进 | 30s | `JobTimeout → 自动重排队` |
| 数据库备份 | `db_backup` 接口 | 1h | 文件落盘 + 新鲜度监控 |

### 2.4 发布流程（CI 到生产）

```
GitHub Actions CI          # 单元 + E2E 冒烟
   ↓ 触发 release.yml    # 生成 release tarball + 镜像
   ↓ 传到堡垒机 / SCP
   ↓ 堡垒机执行 deploy/upgrade.sh  # 90s 健康门禁 → 自动回滚
```

`upgrade.sh` 细致流程：

1. `tar -czf` 现网 `~/upgrade-backups/<ts>/`（含 `data|uploads|outputs|auth.json`）；
2. 解包发行包 → 覆盖 `backend/app|config|scripts|frontend/dist`；
3. 仅重启 `backend`（:8000）；GPU 模型服务不动；
4. 60s 内 `GET /health` 200；第 90s `GET /health/services` `all_online:true`；
5. 门禁失败 → 回滚到备份 → 再次拉起；
6. 退出码：0=ok / 1=rollback / 2=rollback 后仍异常（看 `~/backend.log`）。

> 回滚演练记录见 P2 验收；自动保留最近 5 份升级备份。

### 2.5 灾备与恢复演练内容

- **数据库恢复**：停后端 `fuser -k 8000/tcp` → 解包覆盖 `data|uploads|outputs` → `bash ~/backend_g0.sh`；`auth.json` 损坏自动回退 `.bak`。
- **机器重启**：`bash ~/start_all.sh` 一条命令完成依赖顺序与就绪等待；
- **孤儿 GPU 进程**：`nvidia-smi --query-compute-apps=pid` → `kill -9`（勿 `pkill` 按名称）；
- **忘记管理员密码**：停后端 → 编辑 `auth.json` 删除用户 → 重启 → `/auth/setup` 重建（仅剩余 0 用户时）。

## 5. 风险与启动会当场拍板事项

### 5.1 风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 驱动/CUDA 版本不匹配 | 中 | 阻塞 | P0 核对驱动；统一重装 |
| 模型离线无法下载 | 低 | 延期 | 准备离线介质 |
| 显存不足 | 中 | 慢/oom | 关闭视觉链路；降并发；清孤儿 |
| 真实样本分布偏 | 中 | 效果差 | P3 试运行调优 |
| 第三方商用授权 | 低 | 合规 | 明确是否商用；提前采购 |
| 升级回滚演练失败 | 低 | 停机 | 在预演环境练习 |

### 5.2 启动会当场决策

1. **部署形态**：裸机双卡还是 Docker Compose？
2. **访问形式**：IP/DNS + 端口？TLS + 反向代理方案？
3. **身份认证**：是否启用 LDAP/AD？同步组映射？
4. **数据库连通**：客户 DB 只读账号与网络连通性？
5. **内网文件接入**：目录导入还是 SFTP 拉取？
6. **培训场次与名单**：管理员 / 用户 / 运维人数与时间；
7. **验收标准**：冒烟 + 黄金语料阈值；
8. **上线截止日期**。
